开发工具与智能体分区先读

两套编码技能混搭：用文档、剧本和子代理管理AI开发流程

UP主展示把 Matt Pocock 的 Skills 与 pstack 组合成个人 AI 编程工作流：先用需求对齐技能沉淀术语表、ADR、规格和工单，再让 pstack 的 /poteto-mode 从 22 个剧本中选择 bug 修复、功能开发或原型路径，分派子代理并在待办中留下跳过原因；最后用测试、真实运行输出和另一模型评审验收。作者还写了 /liang-mode 约束何时读取哪套技能。

为什么值得看

重点不是单次生成代码，而是用文档、剧本、子代理和可重跑证据管理多项目并行开发，回应 AI 代码超出人工审阅速度的问题。

实现链路

链路为 /grill-with-docs 明确需求→/to-spec 或 /to-tickets 拆规格/工单→/poteto-mode 选剧本并调度子代理→TDD/架构/评审技能→真实运行输出与独立评审；自定义 mode 负责路由。

最小复现思路

在低风险小仓库中只复现“需求文档—工单—子代理实现—独立评审—真实运行证据”闭环，记录耗时、返工和失败点，再决定是否扩展到多项目。

已知与推测

来源披露：UP主口述其工作流；所引两个 GitHub 仓库已核验为公开页面，但未审计代码，也不等于作者完整实现。

成本与风险

依赖多模型调用与订阅额度，token 和并行代理成本可能上升；子代理评审若同源模型会共享盲区；pstack 镜像与上游可能不同步；流程复杂本身会增加维护成本。

边界与疑点

AI字幕未经人工校对；效果来自单人实践，无量化效率、缺陷率或成本数据；公开仓库未运行、未审计。

内容自动化流水线：定时抓热点、写稿配图与发布看板

UP主展示一套内容自动化流水线：定时任务在早上抓取某热榜平台（ASR 记为 top hub）及其他平台热点，按相关性筛选后进入“内容工厂”，经 skill 流程写稿、配图、排版并归档；另有看板统计待发布、制作中、已制作和已发布状态。微信侧按 10 点写稿、11:30 配图、12 点排版分时运行。作者称每个“员工”是带流程和技能的代理，但未展示提示词、接口、失败率和收益。

为什么值得看

把热点发现、内容生产、视觉排版和发布状态管理串成可调度流水线，展示了小作者也能搭自动化内容工厂，但价值取决于质量控制。

实现链路

来源披露：定时触发抓取热榜/平台热点→相关度筛选→内容工厂调用写作与配图 skill→视觉设计/排版→看板与内容库状态管理；Codex 多线程承担并行任务。

最小复现思路

选一个垂直主题和 3 个允许抓取的来源，先跑一周半自动流程：只生成草稿与配图，人工审核后再发布，记录热点命中率、返工时间和事实错误。

已知与推测

来源披露：UP主口述并展示（ASR）；未核验界面操作、数据准确性或实际发布结果。

成本与风险

依赖热榜接口/抓取稳定性、模型调用费、图片版权与平台规则；自动发布有事实错误和账号风险；同质化内容竞争激烈，缺少收益证据。

边界与疑点

AI字幕未经人工校对，平台名与数量可能误识；未核验看板数字、自动化覆盖率和任何收入。

开发工具与智能体

DSH角色状态插件：提示词注入、衰减与手动面板

短视频演示给 DSH 增加角色状态（作者称“性欲”）的插件更新：状态数值会写入每轮提示词，影响回复方式和主动性；被冷落或睡眠后数值变化，约 1—1.5 小时恢复一部分，面板按钮可手动调整，也可让某次会话静默半小时后在下一次对话提醒，作者称不会主动发消息。片段未展示代码与安装方式。

为什么值得看

显示对话代理插件可用持久状态变量和提示词注入塑造角色行为，涉及代理记忆、拟人化与用户误导风险。

实现链路

来源披露：插件维护状态值→每轮拼入提示词→按时间/互动更新并允许面板手动调节→限制不主动发消息；具体存储、代码与模型未披露。

最小复现思路

在隔离对话中用中性状态变量做小 A/B：同一问题下比较有无状态注入的回复差异，并检查是否出现越权主动推送或情感误导。

已知与推测

来源披露（ASR，未核验画面/代码）；状态如何计算、衰减曲线和提示词模板均属未知，不能推测为固定算法。

成本与风险

缺少源码和安装说明，复现成本高；拟人化状态可能造成依赖或误解，平台对自动消息和情感内容有合规边界；无稳定性数据。

边界与疑点

AI字幕错漏较多，标题和口播中的数值/恢复时间未经人工核对；不能确认插件已发布或可安装。

开发工具与智能体

三款旗舰模型挑战三个遗留Bug：修复轮次与改动规模对比

视频作者让Fable5.2、GPT 6.2 Astra、Gemini Carbon在三个遗留Bug上各最多修三轮，记录耗时、改文件数和验证结果。GPT 6.2 Astra两轮通过最高难K004，Gemini Carbon与Fable5.2在该题三轮失败；低难度题各家轮次也不同。

为什么值得看

遗留代码修复是智能体编程的高价值场景；这类多轮修复赛能暴露模型在定位、改动范围和验证闭环上的差异，但单视频结果只能当线索。

实现链路

按题给出提示词，模型修改代码库；每轮启动服务并跑验证，失败可再改，最多三轮；按通过轮次计分，同时记录耗时和修改文件数。

最小复现思路

复现需固定同一代码库、提示词、验证脚本和模型版本，做多题多轮盲测，并保存补丁与日志；先小规模跑通一题再扩展。

已知与推测

来源披露：轮次、耗时、文件数和通过/失败均来自视频口播字幕；未逐帧核验画面、代码与验证脚本，模型名称按标题/字幕整理。

成本与风险

依赖模型版本、提示词、代码库和验证环境；样本仅三题、单次运行，易受随机性与ASR误识影响；不能据此推断真实开发效率或商业收益。

边界与疑点

仅一个B站视频，AI字幕未人工校对；未核验画面、源码、测试脚本和结果可重复性；模型名称与表现均为视频披露，不代表独立实测。
