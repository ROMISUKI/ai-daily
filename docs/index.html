开发工具与智能体

Karpathy 用 Claude Code 将 4300 万条 HN 评论筛成 HackerTube 推荐站

Karpathy 发帖称，他因不满 YouTube 推荐，用 Claude Code/Opus 5.5 在约两小时内把 20 年 HN 的 4300 万条评论过滤为 6,454 个被反复推荐的视频，做成 HackerTube；状态保存在本地浏览器会话，缩略图取视频中段代表帧，并公开评论分析压缩包供他人让 Claude 生成自己的版本。流程还包括申请 Google Cloud API key、购买 VPS 与域名，再让 Claude 部署、加固和优化。该帖是作者自述，效果未独立复现。

为什么值得看

展示了一条“把大规模历史讨论当推荐信号”的轻量产品化路径，以及 coding agent 从写代码扩展到数据清洗、部署运维的完整闭环；对无登录、可自托管的推荐工具是低成本实验。

实现链路

作者披露：Claude Code（Mac 桌面端）默认使用 Opus 5.5 Medium effort；人工只做 Google Cloud API key、开 VPS、买域名，随后把 IP 交给 Claude 要求更新、安全加固、部署和优化；本地会话保存状态，缩略图从视频中段取帧；分析数据以 zip 公开，可让 Claude 基于该数据生成变体。

最小复现思路

最小复现可先取一小批 HN 评论与视频元数据，要求 agent 输出可解释的推荐列表，再本地做静态页面；先验证筛选规则与重复推荐去重，不要一开始就购买域名或开 VPS。

已知与推测

来源披露：以上来自 Karpathy 原帖自述；所附视频/图片未核验，未独立运行 HackerTube 或复核 4300 万到 6,454 的筛选质量。

成本与风险

依赖 Claude Code/Opus 5.5、YouTube 元数据 API、VPS 与域名；具体成本未披露；需注意 YouTube API 配额与条款、HN 数据使用、API key 与服务器安全；推荐偏差和“显著更好”属作者主观体验。

边界与疑点

仅原帖正文，未核验所附视频；无独立基准、用户研究或代码审计，不能把作者体验当普遍效果。

DSH SuperAgent 插件演示：文件落地触发自动归档与经验注入

B站视频演示在 DSH 桌面端安装 dsh-superagent-prototype 插件，侧栏出现 Superagent；用户把“下载的作业 PDF 自动归位”写入经验库，触发条件为 file created。下载文件后，文件监听发出信号，Agent 自开会话判断是否作业、检查目标目录并移动，全程未再下指令。视频还设想 Minecraft 崩溃日志触发读日志、定位模组、改配置、重启。仓库 README 显示这是 DeepSeek 原型的 fork，增加本机 MSP 推送感知与经验库；但仓库自承经验到行为改变仍未验证，测试也有失败项。

为什么值得看

把 Agent 从“等人提问”推向事件驱动与常驻自动化，展示本机文件系统等非云 API 信号如何进入 Agent 编排；对桌面自动化、个人工作流和插件化感知层有参考价值。

实现链路

来源披露：桌面端设置到插件添加仓库地址并重启，侧栏出现 Superagent；fork 增加 MSP Source，把文件创建等本机信号以推送方式转为 Trigger，经验以 Markdown 保存条件、动作、理由，命中后注入评估上下文。演示链路为 file created、判断作业、检查目标目录、移动文件。

最小复现思路

低成本验证：在隔离目录监控一个测试文件，定义一条只移动 .pdf 到指定文件夹的经验，记录触发、决策和回滚日志；再测试误触发与权限边界，不要直接用于重要文件。

已知与推测

来源披露：视频 AI 字幕（未人工校对）和仓库 README 描述了安装与最小示例；未独立安装、未核验画面。仓库自述经验到行为改变未验证，1202 用例中 1153 通过、42 失败、7 跳过。

成本与风险

依赖 DSH 桌面端/插件、Node 与仓库实现；Windows 有进程发现和锁文件限制；自动移动或改动文件有数据丢失与越权风险；经验规则可能误判，测试覆盖和跨平台稳定性不足。

边界与疑点

仅读到 B站 AI 字幕（未人工校对）和仓库公开页，未逐帧核验；仓库自承关键闭环未验证，不能视为成熟生产方案。

游戏与仿真

Video-to-Game：把 10 到 15 秒游戏视频重建为可玩的 Three.js 网页游戏

候选视频所列的 Video-to-Game 项目提供一套给 coding agent 的 skill：先从一段 10 到 15 秒游戏视频抽取帧、色板与剪辑点，写出镜头、主角、核心机制和关键瞬间的规格；再用 fal 上的图像、3D 和音频模型生成资产，由 agent 在 Three.js 中写游戏，并用键盘场景自测、录制最佳片段。项目页称已用该方法重建 31 个游戏，共 1013 次 fal 调用、约 202 美元，约 6 美元每个游戏；每个游戏是单个 index.html。该汇总视频仅以时间戳提及项目，未读字幕，成本与效果均为项目页自述。

为什么值得看

展示一种“视频当设计文档、agent 当实现者”的游戏原型流水线，把生成式资产与可编辑代码结合；对快速验证玩法和降低 3D 原型门槛有参考价值，但离商业级游戏制作仍远。

实现链路

项目页披露：study_video.py 把视频转成帧、contact sheet、palette 和 cut times；agent 从命名帧写 spec；fal_asset.py 调用图像、3D、音频和音乐模型生成资产；游戏用 Three.js 写成单页；record_play.mjs 以真实帧率录制，best_window.py 找最有活力的片段，形成视频与游戏的并排对比。

最小复现思路

最小验证：选一段 10 秒视频，只重建一个核心机制与一个场景，先用少量 fal 调用生成资产，输出可玩的单页并录一段自测；记录失败帧和成本，再决定是否扩展。

已知与推测

来源披露：项目 README 给出了 31 个示例、1013 次 fal 调用和 202 美元总成本；候选视频只列标题和时间戳。未运行项目、未核验每个游戏可玩性，也未审计生成资产许可。

成本与风险

依赖 fal 付费调用、Python/ffmpeg/Node/Playwright、Three.js 与手工调参；示例均摊约 6 美元每个游戏，但实际随资产量波动；生成资产和视频风格可能涉及版权与平台许可，自动录制不能替代真实玩家测试，单文件游戏也缺乏工程化与性能保障。

边界与疑点

候选视频简介仅按时间戳列出项目，未读字幕、未逐帧核验；项目页的成本、31 个游戏和效果均为作者自述，非独立基准。

音视频与创作

DuET：把钢琴演奏转成可编辑五线谱的开源链路

开源项目 DuET 把钢琴演奏转成可编辑乐谱：先用 Transkun v2 将纯钢琴音频转成演奏 MIDI，再由 DuET 从小节、拍号、调号、时值量化、左右手与装饰音等结构信息生成 MusicXML/MIDI/PDF，可导入 MuseScore 修改。在线 demo 只处理前 4 分钟，受 Hugging Face ZeroGPU 额度限制；代码 MIT，模型权重 CC BY-NC 4.0 仅非商业。作者称纯钢琴效果最好，混入人声或其他乐器会下降。

为什么值得看

它补的是音频转MIDI之后“演奏时间到乐谱结构”的难点，直接面向练琴、扒谱和音乐教育等可编辑谱需求；开源代码与权重降低了复现门槛，但非商业权重限制商用。

实现链路

来源披露的链路是：钢琴音频→Transkun v2 演奏MIDI（或直接输入MIDI）→DuET 估计拍/小节并量化音符、分左右手、判断调号拍号等→导出 MusicXML、试听 MIDI 与结构化结果。视频/简介称可导出 PDF；GitHub README 说明 CLI 不生成 PDF，二者范围不同，未实测。

最小复现思路

可计划用公开 demo 或本地 CLI 对一段纯钢琴短录音生成 MusicXML，核对拍号、小节线与左右手分配，并与人工谱对比；不执行安装或上传。

已知与推测

来源披露：完整AI字幕（未人工校对）与已核验的公开GitHub README；未逐帧核验画面，未独立测试准确率、延迟或PDF导出。未补充未知模型细节。

成本与风险

依赖 Python 3.11+、PyTorch、可选 FFmpeg/Transkun；本地推理需 GPU/内存，在线 GPU 额度有限。模型权重非商业许可，商用需另行授权；复调、非钢琴与复杂节奏准确率下降，可读性后处理还会改动时值分组。

边界与疑点

AI字幕未经校对，项目名/术语有误识别；在线 demo 限前4分钟，效果与 PDF 生成未独立核验；GitHub 公开页面不等于运行或审计代码。

Roblox 故障 TAS 蒙太奇：逐帧工具探索游戏边界

SilverYT 发布 Roblox 故障 TAS 蒙太奇，作者称制作耗时 27 小时、列出 TAS Retakes 54//22，并在 30 多个 TAS 中发现 200+ 新 glitch，使总数超过 5000。视频是工具辅助速通/超级游玩展示：用逐帧精确输入、存档状态、分支与内存读取等工具追求理论上限，而非实时人类纪录。简介给出两个 Roblox 体验链接和 TAS 难度 10/10，但未说明每条故障的具体复现条件。

为什么值得看

它展示了 TAS 作为游戏机制研究工具的价值：通过极端输入探索正常玩家难以复现的边界，但需与实时人类速通纪录区分，平台规则和版本差异会影响可复现性。

实现链路

简介给出 TAS 的通用实现方式：在模拟器/工具中逐帧控制输入，配合存档状态、分支、重录、拼接、内存读取、宏与脚本自动化；本片具体使用的工具链未在已读证据中说明，不能推断。画面/故障细节尚未逐帧核验。

最小复现思路

可计划先核对两个公开 Roblox 体验的版本与路线，选择单段公开可复现的 glitch 做逐帧输入记录，再与原片对照；不执行游戏操作或绕过平台限制。

已知与推测

来源披露：标题、简介与精确发布时间；简介自报耗时、重录和 glitch 数量。通用 TAS 定义来自简介；本片具体路线、工具与画面未核验，不把通用定义当作本片实现细节。

成本与风险

依赖游戏版本、Roblox 平台规则与 TAS 工具兼容性；逐帧研究和剪辑耗时高，版本更新会使路线失效。TAS 结果不是实时人类纪录，也不代表普通玩家可稳定复现；公开游戏链接不等于授权修改或自动化。

Mac 离线运行 22 个 AI NPC 的村庄游戏原型

作者在 Mac 上做一个离线运行的中世纪村庄游戏，简介称有 22 个 AI NPC：Nemotron 把玩家语音转文本，LM Studio 中的 Qwen 3.8 生成回复，Fish Audio Drama 3 合成角色语音，角色约 1.5 秒开始回应，并能记住玩家说过的话、彼此八卦。美术、场景和过场用 Higgsfield、Nano Banana Pro 与 Seedance 2.5 生成；视频由 Higgsfield 赞助，并附构建指南推广链接。

为什么值得看

它把本地小模型、语音交互、持久记忆和多角色社会行为串成游戏原型，指向低延迟离线 NPC 的产品方向；但赞助与作者自报意味着需把演示效果和可复现性分开看。

实现链路

来源披露的链路是：玩家语音→Nemotron STT→LM Studio 本地 Qwen 模型生成对话→Fish Audio TTS 输出角色语音；角色记忆与八卦机制、22 角色如何共享模型在简介/章节中被提及，但具体实现未读字幕，不能推断。

最小复现思路

可计划在 Mac 上用 LM Studio 加载一个小型本地 LLM，接一个 STT 和一个 TTS 做单角色对话原型，测首响延迟与内存，再决定是否扩展多角色共享模型和记忆；不执行安装或游戏开发。

已知与推测

来源披露：视频简介、章节与赞助披露；未读字幕、未核验本地运行画面。1.5 秒延迟、22 角色、离线与记忆效果均为作者声称；模型链按简介记录，不补充未知组件。

成本与风险

依赖本地 Mac 内存/算力、模型与语音许可、离线资产和工程集成；多角色共享模型会增加延迟与状态管理复杂度。视频含赞助和推广链接，存在宣传偏差；平台/版权与生成美术合规需自行评估。

边界与疑点

仅标题/简介/章节，未读字幕、未逐帧核验；22 角色、1.5 秒响应、离线与记忆/八卦行为均为作者自报，未独立测试。赞助关系需披露。

DSH实时视觉插件See Now：按画面变化抽帧再拼图

作者发布给DSH使用的实时视觉插件See Now，核心不是定时截全屏，而是先用HSV网格变化分判断帧是否值得看，再按切点或积分阈值留帧，拼成一张图交给模型。仓库称可接屏幕、摄像头和视频文件，并提供逐场景模式、悬浮窗与调试工具；商业用途需书面授权。视频仅看到标题/简介，字幕因与主题不符弃用，技术细节主要来自公开仓库。

为什么值得看

实现链路

实现链路（据仓库披露）：采集屏幕/摄像头/视频，在64×36 HSV网格计算帧变化分，用绝对切点、尖峰和秒级不应期，以及积分阈值筛帧，再按档位选择格子并拼图，输出PNG交给DSH模型；悬浮窗仅通过say通道播报。参数和性能数字为仓库自述，未独立复核。

低成本验证
